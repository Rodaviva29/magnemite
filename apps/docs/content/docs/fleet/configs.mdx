Installing a MITM is half the job. Aegis, Atlas and GoCheats all read a JSON file
next to themselves and do nothing useful until it is there and correct — an
account, a Rotom URL, a secret, and the name this particular box reports under.

That file lives on the **device group**, in **Settings → Device groups → MITM
data**, because that is the shape the answer has: two sites talking to two Rotom
instances are two groups, and a config that could only be set once could not
describe them both.

## What a group declares

| Field                | What it is                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| **MITM package**     | The scanner these boxes run. Also what the [MITM column](/docs/fleet/health#the-mitm-column) shows. |
| **Column header**    | Shorter name for that column. Defaults to the last dotted segment.                                  |
| **Config file path** | Where the file goes on the box: `/data/local/tmp/aegis_config.json`.                                |
| **Config JSON**      | The file's contents, with placeholders.                                                             |

The **Fill from** buttons put in the real shapes for Aegis, Atlas and GoCheats —
paths and key sets. These are not guessable: `rotomUrl` on one is `rdmUrl` on the
next, GoCheats uses snake_case and a plain `config.json`, and a wrong key is a
scanner that starts and does nothing.

## Placeholders

Anything a box has to say about itself is a placeholder, substituted per box
before the file is written — the same job aconf does with
`sed 's,dummy,$origin,g'`.

```json
{
  "authBearer": "s3cret",
  "deviceName": "{{device.name}}",
  "rotomUrl": "http://rotom.lan:7072",
  "workers": 8
}
```

Available: `device.id`, `device.name`, `device.serial`, `device.model`,
`device.manufacturer`, `device.androidVersion`, `device.abi`, `device.localIp`,
`device.publicIp`, `device.rotomOrigin`, `device.rotomDeviceId`, `group.name`.

Two things are refused rather than papered over:

- **An unknown placeholder.** `{{device.nmae}}` would otherwise be written
  through literally, and a scanner started against that is worse off than one
  never configured. Caught at Save.
- **A known placeholder with no value on a box.** Substituting `""` is how a
  whole site ends up reporting to Rotom under the same blank origin. Caught when
  the config is rendered for a deploy, naming the box and the field, and logged
  as a warning on that box's job.

<Callout title="rotomOrigin is empty until Rotom matches the box">
  So a first deploy on a fresh fleet often refuses it on most boxes. That is the
  refusal working. Either use `{{device.name}}` — which every box has — or deploy
  again once the Rotom sync has run.
</Callout>

The list is deliberately an allow-list and not "any column on the device row":
that row holds each box's `tokenHash`, and a template able to name it would be a
way to write the fleet's credentials into a file the scanner reads.

## When it is written

One path: **with the install.** A rollout of a group's own MITM carries that
group's config. The agent writes it after the install verifies and **before** the
post-install hook — which is the hook that starts the scanner, so it never starts
against the previous site's config. A rollout of any other package carries
nothing; the package match is the whole gate, and there is no switch for it
anywhere.

Saving a group writes to the database and nothing else. An edited config reaches
the fleet on the next deploy of that group's MITM, and not before.

<Callout type="warn" title="There is no separate push">
  There was one, with a restart command to make the running scanner re-read the file. Both are gone:
  inside an install the post-install hook already restarts the scanner, so the command only earned
  its keep on the push, and the two only made sense together. Changing a config now costs a deploy
  of the MITM — which for a large fleet is an APK download per box.
</Callout>

## How it lands

Not a shell command with a heredoc, which is how this would otherwise be done.
The agent takes the `config` object off the install job and:

1. Refuses the path if it is relative, un-normalised, under `/system`,
   `/vendor`, `/product`, `/apex`, `/proc`, `/sys`, `/dev` or `/boot` — or if it
   is the agent's own `config.json`, which holds this box's device token.
2. Writes to a temp file and **renames** it into place, so a scanner reading the
   file while it is replaced sees the old bytes or the new ones, never a
   half-written middle.
3. Reads the file back and reports its sha256. That answers "what is on the box",
   where hashing what the hub sent would only answer "what did the hub mean".

A config that cannot be written **fails the job**, rather than leaving a scanner
running on someone else's settings. The downloaded bundle is kept, so the retry
costs an attempt and not a second download.

<Callout type="warn" title="The config holds credentials">
  `authBearer`, `deviceAuthToken`, an email address. It is never written to the hub's log, never
  into an audit entry, and never sent to a VIEWER's browser — they are told a config exists, not
  what is in it.
</Callout>

## Old agents

A box on an agent from before this existed drops the field in silence, so the hub
checks what each agent reported it can do in its `hello` before attaching a
config. An install onto such a box installs normally and logs a warning on the
job, which resolves itself once the box takes its next agent update.

## Lineage

The paths and the per-box name substitution are both
[aconf](https://github.com/TechG3n/aconf)'s, which has been doing this on the
same hardware for years. What changes here is where the answer lives: rows in a
database that one person edits, rather than a file per box.
