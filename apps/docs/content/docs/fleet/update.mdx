import { Step, Steps } from "fumadocs-ui/components/steps";

<Steps>

<Step>

### Check the free space

This is important, it refuses to start unless `/data` has roughly **3× the bundle size** free. A
172 MB `.apkm` unpacks to about 250 MB, and both sit on disk at once.

</Step>

<Step>

### Wait for system_server

`service check package` and `service check activity`, until both answer. Almost always instant.

It matters on a retry: an install heavy enough to take system_server down leaves the box rebuilding
its Android for the best part of a minute, with the kernel and the agent running straight through
it. Without this wait, `am` reports `Can't find service: activity` and `pm install-create` reports
`Can't find service: package` — a healthy box burning an attempt in under a second.

</Step>

<Step>

### Run the pre-install hook

Usually stopping the scanner/MITM. Configured per device group, or overridden per rollout.

Before the download, not after it: the scanner is what saturates the uplink on these boxes, and a
170 MB pull sharing it costs the scanner its Rotom socket. It reconnects with no backoff at all,
and that storm is still going when the install asks system_server for the heaviest thing it ever
does.

</Step>

<Step>

### Download and verify

Fetch the `.apkm` from your server with a `Range` header, so a box that drops
its uplink at 80% resumes instead of starting over. Verify the sha256 the hub
computed while caching.

</Step>

<Step>

### Pick the splits

An `.apkm` is a zip holding `base.apk` plus `split_config.arm64_v8a.apk`. The
agent selects base plus the matching ABI, and the nearest density and language
splits if the bundle has them.

</Step>

<Step>

### Install the session

```sh
pm install-create -r -d -i com.android.vending
pm install-write …   # once per split
pm install-commit …
```

A plain `pm install` cannot take a split bundle, which is why this is a session.

</Step>

<Step>

### Fall back to a clean install, if Android insists

If Android rejects the in-place upgrade, like a different signing key, or a
downgrade, the agent uninstalls and installs clean. **This wipes the app's
data**, so the job is flagged as `data wiped`.

</Step>

<Step>

### Verify

`dumpsys package` has to report the expected version. `pm` printing _Success_
is not taken as proof.

</Step>

<Step>

### Run the post-install hook

Usually starting the scanner again or a personalized command.

It runs on **every** way out, not only the successful one — a download that 404s, a commit that
takes system_server with it, a job that hits its deadline. The pre-install hook stopped the box;
something has to start it again, and the moments a box is most likely to be left stopped are the
ones nobody is watching.

</Step>

</Steps>

Every step keeps progress over the socket, so we get a real
percentage and the box's own log.

## In-place vs clean

The default approach preserves app data and only falls back to a wipe when Android
insists. Ticking **force a clean install** on a rollout uninstalls first on
every device.

<Callout type="warn">
  A clean install is the right answer when the signing key changed and you know it. It is the wrong
  answer as a habit.
</Callout>

## What the agent never does

It runs as root but changes **no device settings**. It installs, reads package
versions and free space, and runs the hooks you configured: **nothing else**.
