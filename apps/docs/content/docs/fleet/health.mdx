The device page's **Load** card shows what a box is doing right now, with the
last hour behind each number as a sparkline. The chart icon in its corner opens
**Load history** — the same readings over a window you choose.

## What the box reports

Every heartbeat — one every 20 seconds — the agent reads a handful of small
`/proc` files and sends them along with the package versions:

| Reading         | Where it comes from                              |
| --------------- | ------------------------------------------------ |
| CPU load        | `/proc/loadavg`, against the box's core count    |
| Memory          | `MemTotal` and `MemAvailable` in `/proc/meminfo` |
| Storage         | `/data` — the partition an install writes to     |
| Temperature     | `/sys/class/thermal/thermal_zone*`               |
| CPU/RAM per app | `/proc/<pid>/stat` and `statm`, per tracked app  |

Two of those need explaining.

**Temperature.** Plenty of TV boxes expose no thermal zone at all, and the ones
that do disagree about units — millidegrees on most, deci-degrees or plain
degrees on some Amlogic and Rockchip trees. The agent picks the divisor by
magnitude and drops anything that lands outside −30 to 150 °C, so a box that
cannot say shows no temperature rather than a wrong one. Where the zone is
unlabelled, the hottest one is used: whatever is closest to throttling is what
matters.

**Per-app usage.** Only the [tracked packages](/docs/fleet/columns) are
measured, summed across every process the app owns — an app with a `:remote`
service is one line, not two. CPU is a share of a _single_ core, the number
`top` shows, so 200% means two cores pinned.

<Callout type="info">
  A reading the box never sent is stored as null and drawn as a gap, never as a zero. That is the
  difference between "the scanner was idle at 3am" and "the scanner was dead at 3am", and it is the
  question the history exists to answer.
</Callout>

## Load history

One filter row scopes everything below it, so every chart agrees with the rest:

- **Time range** — last hour through last 30 days. Presets longer than the
  retention are disabled, because there would be nothing in them.
- **Apps** — which tracked packages the per-app charts draw. Colours are fixed
  per package, so filtering one out never repaints the others. Eight at a time
  is the cap.
- **Table** — the same numbers as text, for when a chart is not what you want.

Each chart carries `avg`, `p95` and `max` for the window under it. The p95 is
there because a mean hides the spike, and the spike is usually what is being
looked for.

<Callout type="info">
  Charts are bucketed to roughly one point per pixel-column before they leave the server — a week at
  a one-minute interval is ten thousand readings per box, which is more than a line can draw. The
  statistics are computed from the raw rows, not the buckets, because an average of averages is not
  the average.
</Callout>

## Retention

Two knobs in **Settings → Tuning**, because how much history is worth its
disk is a per-fleet answer:

| Setting                          | Default | What it does                                                         |
| -------------------------------- | ------- | -------------------------------------------------------------------- |
| Health sample interval (seconds) | 60      | How often a heartbeat is kept. Below 20 just stores every beat.      |
| Health history retention (days)  | 7       | How long samples live. 0 turns recording off and drops what is kept. |

At the defaults a box costs about 1 400 rows a day, plus one per tracked app.
The hub prunes hourly, in batches, so the delete never locks the table against
the heartbeats writing to it.

<Callout type="warn" title="Nothing recorded in this window yet">
  Expected on a box that has just enrolled, and on a fleet running an agent from before these
  readings existed — the fields are optional on the wire, so an old agent simply does not send them
  and updates itself in due course. It is also what you get with retention set to 0.
</Callout>
