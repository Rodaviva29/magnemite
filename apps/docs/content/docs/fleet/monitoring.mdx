A box can be online, heartbeating every twenty seconds, and scanning nothing:
the scanner died, Pokémon GO fell out of focus, an ANR dialog is waiting for
somebody to press ENTER, the loop stalled. None of that shows in the fleet
table, because by every measure it has the box is fine.

**Settings → Monitoring** turns those into rules. A rule is a signal, how many
bad readings in a row it takes to count, and a ladder of what to do — soft
first, hard second.

The **Monitoring** page in the sidebar is the other half: what the rules saw
and did across the fleet, which is where "why did that box reboot at 3am" is
answered.

<Callout type="warn" title="Everything ships disabled">
  A new fleet gets seven rules already written, every one switched off, along with the master
  switch. This feature reboots hardware in someone's living room; nothing here starts happening
  because a deploy went out.
</Callout>

## What it watches

| Signal                      | Answered by                  | What it means                                         |
| --------------------------- | ---------------------------- | ----------------------------------------------------- |
| **Service is down**         | a probe, or the process list | The scanner's service is not running                  |
| **App is not in focus**     | the box                      | Something else owns the screen — usually the launcher |
| **App is not responding**   | the box                      | The package is sitting on an ANR dialog               |
| **Health check is failing** | a probe                      | The scanner is logging faults faster than work        |
| **Loop has stalled**        | a probe                      | The scanner is alive and has stopped doing anything   |
| **Box is unreachable**      | the hub                      | The socket has been gone past the offline timeout     |
| **Rotom lost the box**      | the hub                      | Rotom is not seeing it, or would not hand it work     |

The first five are knowable only on the box, so they need a recent agent — the
tab counts how many boxes are behind, and rules skip a box that cannot answer.
The last two the hub sees for itself and work on every box today; the Rotom one
needs [Rotom turned on](/docs/fleet/rotom).

## The ladder

A rule does the gentle thing first and the expensive thing only when the gentle
one did not work:

```
Scanner offline
  failure 1 → restart the app
  failure 2 → reboot the box
```

The counter resets the moment the signal goes good, so a box that recovers
never reaches the reboot. A rung already spent is not spent again — except the
**last** one, which repeats at the cooldown, because there is nothing stronger
left to try.

| Action                       | What it runs                                          |
| ---------------------------- | ----------------------------------------------------- |
| Only tell me                 | nothing                                               |
| Restart the app              | `am force-stop {pkg}` then relaunch                   |
| Kill the app                 | `am force-stop {pkg}`                                 |
| Clear the cache and restart  | force-stop, delete `/data/data/{pkg}/cache`, relaunch |
| Send ENTER                   | `input keyevent 66` — dismisses an ANR dialog         |
| Start the service            | `am startservice …`                                   |
| Run a command                | whatever you type                                     |
| Reboot the box               | the same reboot the device page sends                 |
| Restart the scanner in Rotom | Rotom's own `restart` action                          |

Every shell-backed one takes an **override command**, `{pkg}` standing in for
the rule's package. The catalog exists so an alert can say "cleared the cache
and restarted" rather than quoting a command line; the override exists because
your MITM is not the one this was written against.

## Probes

Three signals need the box to look at something, and what to look at differs
per MITM — so the probe is part of the rule:

- **Shell command** — runs as root, passes on exit 0, optionally also having to
  match a pattern. `dumpsys activity services | grep -e MappingService` is the
  whole "is the scanner up" check.
- **Pattern in a log** — reads the last N lines of a file and counts matches.
  Can also fail when nothing has been written for a while, which is what a
  stalled loop looks like from outside.
- **HTTP endpoint** — a GET from the box itself; 2xx is healthy.

A log probe can carry a **second** pattern for work getting done, and fail only
when faults outnumber it — ten "seconds since last ping" lines mean nothing
next to a hundred completed jobs and everything next to two:

```
Log file          /data/local/tmp/atlas.log
Lines to read     200
A fault           \[HEALTH CHECK\] ([0-9]+) seconds since last ping\.
Faults before     10
Work looks like   I \| Worker
```

Probes run every heartbeat, inside **half the beat**. Whatever does not finish
in that budget reports nothing at all — never a failure. They are skipped
entirely during an install, because an install force-stops the scanner on
purpose and every probe would report the damage Magnemite asked for.

into a fleet rebooting itself in a loop:

## The numbers

The master switch is on **Settings → Monitoring**. Everything else is the **How
it watches** card on **Settings → Tuning**, because every number in it is
measured against the heartbeat or the offline timeout, which sit directly above.

| Setting                         | Default | What it does · what a bad value costs                                                                                             |
| ------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Act on what it sees**         | off     | Off, no probe is sent and nothing is touched. Rules can still be written.                                                         |
| **Ask Rotom every**             | 60s     | One request for the whole fleet. Everything Rotom-shaped is this fresh at best. Too tight is rude to somebody else's server.      |
| **Rotom stale after**           | 600s    | How long since Rotom saw a box before that counts as disconnected. Floored at two sync intervals, or it alerts on the sync's lag. |
| **Grace · after a reboot**      | 600s    | Shorter than the box takes to boot and its own reboot reads as unreachable — so it is rebooted again, forever.                    |
| **Grace · after a hub restart** | 180s    | A restart drops every socket at once; without this, a deploy looks like a fleet-wide outage.                                      |
| **Actions per box per hour**    | 4       | Circuit breaker. Past it, one critical alert and the box is left alone. This is what bounds a rule that turns out to be wrong.    |
| **Reboots per box per day**     | 6       | The same, counted separately, because a reboot costs a scanning session and the other actions do not.                             |
| **Repeat an alert after**       | 30 min  | The same signal on the same box is not announced again inside this. The action still happens and is still recorded.               |
| **Keep history for**            | 30 days | How long the Monitoring feed is kept. 0 keeps it forever.                                                                         |

The monitor pass itself is not configurable: it runs once per heartbeat,
because a pass reads what the boxes last said and they say it once per beat.
"Box is unreachable" counts from the **offline timeout** — to wait longer,
raise that rule's own threshold, which is per group.

<Callout type="warn" title="The two graces and the two ceilings are the safety of this feature">
  Everything else is tuning. Those four stand between a useful watchdog and a fleet rebooting itself
  in a loop, and each exists because that has happened to somebody.
</Callout>

## Discord

In the **Discord** card on the same tab: a **webhook URL** (empty turns
notifications off and leaves the rules running), a **minimum severity** (below
it a rule acts and is recorded but not announced), and an optional **role to
ping**, used on critical only — a mention on every warning is how a channel
gets muted, which costs you the alert that mattered.

Individual rules can be silenced without being switched off. "Pogo not in
focus" ships that way: a box briefly on the launcher is common enough that
announcing every one teaches people to ignore the channel.

Press **Send test alert** before trusting any of it. It ignores the severity
filter and the repeat window on purpose. A webhook that stops working never
stops the remediation — the box is still restarted, and the Monitoring page
records that the message did not arrive.

## Scope

A rule applies to every box, or to one device group. A group-scoped rule
**replaces** the fleet-wide rule for the same signal and package rather than
adding to it, or two ladders would race over one fault and the box would be
restarted twice. That is the seam for a fleet running Atlas at one site and
Aegis at another.

The group is also where that site declares which MITM it runs and what to write
into its [config](/docs/fleet/configs). A group-scoped rule and its group's MITM
package are two halves of the same answer, so they are worth keeping in step: a
rule probing Atlas's log on a group that runs Aegis is a rule that never fires.

The seeded rules are not invented: their thresholds and ladders are what
[aconf](https://github.com/TechG3n/aconf)'s `atlas_monitor.sh` has done on this
hardware for years. The probe strings are Atlas's, which is exactly why they
are editable rows.
