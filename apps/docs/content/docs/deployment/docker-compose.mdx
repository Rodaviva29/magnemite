`deploy/docker-compose.yml` is the self-hosted deployment: our own Caddy
publishes one plain-HTTP port, serves the dashboard and the artifacts, and
proxies what belongs to the hub. Nothing binds 80 or 443 — the reverse proxy
already fronting your server terminates TLS and forwards to `EDGE_PORT`.

## What runs

| Service | Image / build         | Ports                           |
| ------- | --------------------- | ------------------------------- |
| `hub`   | `apps/hub/Dockerfile` | 3001, internal                  |
| `web`   | `apps/web/Dockerfile` | 3000, internal                  |
| `caddy` | `deploy/edge`         | `EDGE_PORT` (8080) → 8080, HTTP |

No database service: it connects to one you already run, MariaDB/MySQL or
Postgres, over `DATABASE_URL`.

## Configuration

Everything comes from `.env` at the repo root — copy `.env.example`:

```sh title=".env"
EDGE_PORT=8080
MAGNEMITE_PUBLIC_URL=https://magnemite.example.com
DB_PROVIDER=mysql
DATABASE_URL=mysql://magnemite:…@db.example.com:3306/magnemite
```

Both audiences share one virtual host here, so compose derives
`MAGNEMITE_DASHBOARD_URL` from `MAGNEMITE_PUBLIC_URL`. Full list:
[environment reference](/docs/deployment/environment).

```sh
openssl rand -base64 32   # AUTH_SECRET
openssl rand -base64 32   # HUB_INTERNAL_SECRET
```

<Callout type="warn">
  `DATABASE_URL` is resolved inside the container, so a host-published port like `127.0.0.1:5433` is
  the one address it cannot use. And `DB_PROVIDER` has to match the URL: changing it is a
  **rebuild**, because the Prisma Client is generated into the images.
</Callout>

## Running it

| Target         | Runs                                                  |
| -------------- | ----------------------------------------------------- |
| `make up`      | `up -d --build` — admin login works immediately       |
| `make down`    | `down`                                                |
| `make logs`    | `logs -f hub web`                                     |
| `make migrate` | `pnpm --filter @magnemite/db run deploy` inside `hub` |
| `make seed`    | optional starter data and a first enrollment token    |

Without `make`, both flags are required — the compose file lives under
`deploy/`, `.env` at the repo root, and Compose would otherwise start with
every variable blank:

```sh
docker compose --env-file .env -f deploy/docker-compose.yml up -d --build
```

## What your proxy must do

Point one virtual host at `http://127.0.0.1:8080` and terminate TLS. It has to
forward WebSocket upgrades on `/ws/device`, and must not buffer `/api/events`
(SSE, an idle stream that must never time out) or `/files/*` (~170 MB
responses agents resume with `Range`).

Caddy serves `/files/*` off the artifacts volume behind `forward_auth`, proxies
`/ws/device`, `/api/enroll`, `/api/logs/*` and `/healthz` to the hub, and sends
everything else to the dashboard. `/internal/*` is deliberately absent: the
dashboard reaches it over the compose network, nothing outside can.

## Upgrading

```sh
git pull
docker compose --env-file .env -f deploy/docker-compose.yml up -d --build
make migrate
```

Rebuilding `hub` drops every device socket; agents reconnect with backoff and
queued jobs resume. To leave them alone, name the service:
`… up -d --build web`.

## Postgres or MariaDB

Prisma has no `mariadb` provider — MariaDB speaks MySQL's protocol, so
`DB_PROVIDER=mysql` covers both; `postgresql` serves a Postgres.

The two engines keep separate migration histories (`prisma/migrations` and
`prisma/migrations-mysql`), and nothing copies data between them. Decide the
engine once, before the first seed.
