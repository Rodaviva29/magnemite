`deploy/compose.coolify.yml` lets Coolify's proxy terminate TLS and keeps a
small Caddy of our own (`edge`) in front of the hub. It uses **two domains**
rather than path routing, because the agents and the dashboard are separate
audiences.

| Service | Domain for                                                           | Container port |
| ------- | -------------------------------------------------------------------- | -------------- |
| `web`   | the dashboard you log into                                           | `3000`         |
| `edge`  | what the boxes talk to — use a subdomain like `agents.<your-domain>` | `8080`         |

Neither is declared in the compose file. You add them in the Domains tab — see
[adding the domains](#add-the-domains) and [why they are not in the
file](#why-the-domains-are-not-in-the-file).

## Deploying

<Steps>

<Step>

### Create the resource

**New Resource → Docker Compose**, pointed at this repository. The compose file
is resolved from two fields in **Build configuration**, and it is the pair that
matters, not either one alone:

| Field          | Value                  |
| -------------- | ---------------------- |
| Base directory | `/deploy`              |
| Compose file   | `/compose.coolify.yml` |

Coolify echoes the result underneath as **Resolved file:
`/deploy/compose.coolify.yml`** — check that line before continuing.

Both fields are joined, so a full path in one and `/` in the other resolves to
the same file — but the base directory is also the working directory of the
**Custom Build/Start Commands**, so keep it on `/deploy` and the commands stay
the short ones used [to narrow a
deploy](/docs/deployment/zero-downtime).

</Step>

<Step>

### Add the domains

Two things have to line up here, and they are in different tabs. The **Domains**
tab tells Coolify's proxy where to route; the **Environment** tab tells the apps
what to call themselves.

In the **Domains** tab, one domain per service, each with the container port as
a `:suffix` — that suffix is the routing hint, not part of the public address:

| Service | Domain                                      |
| ------- | ------------------------------------------- |
| `web`   | `https://magnemite.example.com:3000`        |
| `edge`  | `https://agents.magnemite.example.com:8080` |
| `docs`  | `https://docs.magnemite.example.com:3002`   |

<Callout type="error" title="The edge port is the one that breaks quietly">
  Miss `:8080` and Traefik routes the boxes' domain to a port Caddy never opened — the dashboard
  keeps working, so nothing looks wrong, while every box gets a 502 on `/ws/device` and on every
  download. `docs` only exists if you deployed `compose.coolify-docs.yml`.
</Callout>

Then, in the **Environment** tab, the two domains again **without** the port —
these are what the boxes and the browser are handed, not routing hints — plus
the database this stack does not run itself:

```sh
MAGNEMITE_PUBLIC_URL=https://agents.magnemite.example.com
MAGNEMITE_DASHBOARD_URL=https://magnemite.example.com
DATABASE_URL=mysql://magnemite:<password>@<db-host>:3306/magnemite
```

`DATABASE_URL` points at a database you deploy separately — see [the database is
not in the stack](#the-database-is-not-in-the-stack). Add `DB_PROVIDER` too if
it is not MariaDB or MySQL.

`MAGNEMITE_PUBLIC_URL` is the one to get right: every artifact URL a box is told
to download from is built on it, so pointing it at the dashboard's domain
enrolls a fleet that can never fetch anything.

</Step>

<Step>

### Deploy

Nothing to run by hand afterwards. The database migrates itself on boot and the
admin account is created the moment the hub starts.

The first deploy has to be the full-stack one, with the **Custom Build/Start
Command** fields empty — narrowing them comes later, once there are sockets
worth protecting. See [deploying without dropping the
fleet](/docs/deployment/zero-downtime).

</Step>

<Step>

### Read the generated admin password

Coolify generates the database password, the internal secret, `AUTH_SECRET` and
the **admin password** itself, and shows them in the **Environment** tab. Read
`SERVICE_PASSWORD_ADMIN` from there to sign in the first time; change it from
**Settings → Accounts** afterwards if you prefer one you can remember.

</Step>

</Steps>

## What you set up from the dashboard

The stack boots empty apart from the admin account: no app target, no version
sources, no groups. That is the first session in the dashboard, not a script —
an app target and its [version sources](/docs/operations/sources) first, then a
group and an [enrollment token](/docs/fleet/enrollment) for the boxes, all under
**Settings**.

<Callout type="warn">
  The UnownHash mirror needs its base URL set to `https://mirror.unownhash.com/apks/`, with the
  trailing path. Without it the index still parses and every download 404s.
</Callout>

## The admin login

The login defaults to `admin@magnemite.com`. Nothing is ever sent to it — the
address is an identifier, not a mailbox — so it only needs changing if you want
your own.

<Callout type="warn">
  Set `ADMIN_EMAIL` **before the first boot** if you want a different one. Changing it later creates
  a *second* admin rather than renaming the first, because the sync upserts on the address.
</Callout>

<Callout type="info">
  There is no `.env` file inside the container, so the hub reads `ADMIN_EMAIL` and `ADMIN_PASSWORD`
  from the **hub** service's environment, on every boot. That is why they are set on `hub` and not
  only on `web`.
</Callout>

## Things this file does differently

### The database is not in the stack

Unlike `deploy/compose.yml`, which runs its own Postgres, this file ships no
database service and no data volume. It connects to one you deploy separately —
its own Coolify resource, or anything else the containers can reach — over a
single `DATABASE_URL`.

`DB_PROVIDER` has to agree with that URL: **`mysql`** for MariaDB or MySQL
(Prisma has no separate `mariadb` connector), `postgresql` for Postgres. It is
interpolated in two places per app service, and both are load-bearing:

- as a **build arg**, because the Prisma Client is generated into the hub and
  web images at build time and has to match the URL it will be given;
- as a **runtime env**, because the hub's entrypoint runs `prisma migrate
deploy`, and the provider is what selects `prisma/migrations-mysql` over
  `prisma/migrations`.

Both read the same `${DB_PROVIDER:-mysql}`, so setting the variable once moves
both and they cannot drift apart. Changing it means a **rebuild**, not just a
restart — the client is inside the image.

<Callout type="warn" title="The URL is resolved inside the container">
  A Coolify database resource publishes an internal hostname on its own network and, optionally, a
  public one. `DATABASE_URL` needs the internal one, and the database has to share a network with
  this stack — a public URL works until Coolify's firewall or a restart moves it.
</Callout>

<Callout type="error" title="Providers do not migrate into each other">
  The two migration histories are separate and nothing copies data between them. Pointing this stack
  at a database of the other kind starts an empty schema, it does not convert anything. Dump and
  restore by hand if you have a fleet already enrolled.
</Callout>

### Why the domains are not in the file

Coolify can generate a domain for a service from a `SERVICE_URL_<name>_<port>`
placeholder, and this file used to do that. It went wrong asymmetrically: `web`
and `docs` came out as `…:3000` and `…:3002`, and `edge` came out as a bare
`http://edge-….sslip.io` with no port at all — pointing the boxes at a port
Caddy does not listen on.

The other half of the problem is that the generated values are not stable.
Coolify keeps a port-carrying variable and a generic one for each service, and
after a domain is edited in the UI the generic pair [is not always
updated](https://github.com/coollabsio/coolify/issues/8912) — it keeps the
autogenerated wildcard domain. `MAGNEMITE_PUBLIC_URL` was read from that generic
variable, which is the worst possible thing to have go quietly stale: it is the
host every box downloads from.

Setting the two domains by hand costs one extra field each and removes both
failure modes. Nothing in the compose file interpolates a `SERVICE_URL_*` or
`SERVICE_FQDN_*` any more; `SERVICE_PASSWORD_*`, `SERVICE_USER_*` and
`SERVICE_BASE64_*` still work as before, because generating secrets is the part
of that mechanism with nothing to get wrong.

### The auth URL fallback

Better Auth without a base URL derives the origin from the incoming `Host`
header, which breaks callbacks behind a proxy. The app resolves one from
`BETTER_AUTH_URL`, then `MAGNEMITE_DASHBOARD_URL`, then Coolify's own
`SERVICE_FQDN_WEB` / `SERVICE_URL_WEB` if they happen to be in the environment.

With the domains set by hand, the last two are not there — which makes
**`MAGNEMITE_DASHBOARD_URL` required on this deployment**, not optional. Leave it
out and logging in fails in ways that look like a cookie problem. A bare host
with no `https://` is accepted.

### Why there is still a Caddy

Coolify's proxy (Traefik) routes; it does not serve files. It has no
`file_server` equivalent, and the `artifacts` volume belongs to this stack, not
to the Coolify-managed proxy container — so pointing the boxes' domain straight
at the hub means every one of those ~170 MB bundles is read and pushed by Node.

The `edge` service closes that gap. It mounts `artifacts` read-only, answers
`/files/*` with `file_server` (native `Range`, so an interrupted download
resumes) behind a `forward_auth` call to the hub's `/internal/authz`, and
proxies only `/ws/device`, `/api/enroll` and `/healthz` through. Everything else
on that domain is a 404, which keeps the hub's `/internal/*` API unreachable
from outside — the same guarantee the Caddy setup gives.

The Caddyfile is **baked into the image**, not bind-mounted, because Coolify
turns a file bind mount into one it manages itself — see [when the Caddyfile
changed](/docs/deployment/zero-downtime#when-the-caddyfile-changed).

## Upgrading from an earlier version of this file

The boxes' domain has been generated three different ways, and none of the moves
needs re-flashing — a box only ever knows the URL, so keeping the same domain
value is enough:

- `SERVICE_FQDN_HUB_3001` → `SERVICE_FQDN_EDGE`, when the edge gained its own
  service.
- `SERVICE_FQDN_EDGE` → `SERVICE_URL_EDGE_8080`, briefly moving the port into
  the variable name.
- No placeholder at all, which is where it is now.

Coming from either of the placeholder shapes: keep the domain, make sure it
carries `:8080`, and **add `MAGNEMITE_PUBLIC_URL` and `MAGNEMITE_DASHBOARD_URL`
to the Environment tab** — they used to come from the generated variables, and
without them the hub boots with an empty public URL.
