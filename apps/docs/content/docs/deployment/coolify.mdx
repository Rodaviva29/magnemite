`deploy/compose.coolify.yml` lets Coolify's proxy terminate TLS and keeps a
small Caddy of our own (`edge`) in front of the hub. It uses **two domains**,
because the dashboard and the boxes are separate audiences, and **no database**
— you point it at one you deploy separately.

## Deploying

<Steps>

<Step>

### Create the resource

**New Resource → Docker Compose**, pointed at this repository, with two fields
under **Build configuration**:

| Field          | Value                  |
| -------------- | ---------------------- |
| Base directory | `/deploy`              |
| Compose file   | `/compose.coolify.yml` |

</Step>

<Step>

### Set two switches before the first deploy

Both live outside the Environment tab, and both are easier to set now than to
diagnose later.

| Where             | Switch                        | Set it to               |
| ----------------- | ----------------------------- | ----------------------- |
| **Advanced**      | Connect to Predefined Network | on                      |
| **General → Git** | Auto deploy                   | Manual deployments only |

**Connect to Predefined Network** puts these containers on Coolify's shared
network instead of a private one of their own. That is what makes the database
resource resolvable by the internal hostname `DATABASE_URL` uses — without it
the hub boots, fails to connect, and the migration never runs.

**Manual deployments only** stops a push to the default branch from
redeploying. A deploy recreates `hub` and takes every device socket with it, so
the fleet should drop when _you_ decide, not when a commit lands — see
[deploying without dropping the
fleet](#deploying-without-dropping-the-fleet).

</Step>

<Step>

### Add the domains

In the **Domains** tab, one per service — bare, with no `:port` suffix. Each
service declares its container port in the _name_ of a `SERVICE_URL_*` variable
(`SERVICE_URL_EDGE_8080`, `SERVICE_URL_WEB_3000`, `SERVICE_URL_DOCS_3002`), and
that is what tells the proxy where to route:

| Service | Domain                                 | Port carried by         |
| ------- | -------------------------------------- | ----------------------- |
| `web`   | `https://magnemite.example.com`        | `SERVICE_URL_WEB_3000`  |
| `edge`  | `https://agents.magnemite.example.com` | `SERVICE_URL_EDGE_8080` |
| `docs`  | `https://docs.magnemite.example.com`   | `SERVICE_URL_DOCS_3002` |

Each declaration also yields a generic `SERVICE_URL_EDGE` / `SERVICE_FQDN_EDGE`,
and that is what the apps read. `docs` only exists if you deployed
`compose.coolify-docs.yml`.

<Callout type="warn" title="Read the generic value back after editing a domain">
  Coolify updates the port-carrying variables when a domain changes in the UI, but [not always the
  generic pair](https://github.com/coollabsio/coolify/issues/8912), which keeps the autogenerated
  wildcard — and that is what every box downloads from. Check it in the **Environment** tab after
  any domain edit, and override it with `MAGNEMITE_PUBLIC_URL` if it is stale.
</Callout>

</Step>

<Step>

### Set the environment

In the **Environment** tab, the database this stack does not run:

```sh
DATABASE_URL=mysql://<user>:<password>@<host>:3306/<database>
```

The two URLs the apps hand out come from the generated domains — `edge`'s for
`MAGNEMITE_PUBLIC_URL`, `web`'s for `MAGNEMITE_DASHBOARD_URL` — so there is
nothing to type unless you want to override one:

```sh
# Optional. Set either one and it wins over the generated domain.
MAGNEMITE_PUBLIC_URL=https://agents.magnemite.example.com
MAGNEMITE_DASHBOARD_URL=https://magnemite.example.com
```

`MAGNEMITE_PUBLIC_URL` is the one to get right: every artifact URL a box is
told to download from is built on it, so the dashboard's domain here enrolls a
fleet that can never fetch anything. `MAGNEMITE_DASHBOARD_URL` is what Better
Auth builds callbacks from and what alert links point at.

The four parts of `DATABASE_URL` are the database's own user, that user's
password, the hostname **this stack** can reach it on, and the database name.
Nothing there is a service name from this compose file:

```sh
DATABASE_URL=mysql://magnemite:s3cret@magnemite-db-abc123:3306/magnemite
```

The user and the database are both commonly called `magnemite`, which is what
makes the shape confusing to read: two different things that share a name. Add
`DB_PROVIDER` if the database is not MariaDB or MySQL.

</Step>

<Step>

### Deploy

Nothing to run by hand: the database migrates itself on boot and the admin
account is created when the hub starts. The **first** deploy must be the
full-stack one, with the custom build/start command fields empty.

</Step>

<Step>

### Read the generated admin password

Coolify generates the internal secret, `AUTH_SECRET` and the admin password,
and shows them in the **Environment** tab — `SERVICE_PASSWORD_ADMIN` is the
first login. To change it, change `ADMIN_PASSWORD` and restart the hub; that is
also the [way back in](/docs/operations/accounts) if it is lost.

</Step>

</Steps>

The stack boots empty apart from the admin: set up an app target and its
[version sources](/docs/operations/sources), a group, and an [enrollment
token](/docs/fleet/enrollment) from **Settings**.

## Deploying without dropping the fleet

Coolify rebuilds every service with a `build:` under a tag carrying the current
commit, so a plain deploy recreates the lot — fine for `web`, fatal for `hub`,
which takes a couple of hundred device sockets with it.

Narrow it with the resource's **Custom Build Command** and **Custom Start
Command** (General tab). They run from the base directory, and Coolify injects
`-f` and `--env-file` itself.

| Changed               | Build command                   | Start command                             |
| --------------------- | ------------------------------- | ----------------------------------------- |
| Dashboard only        | `docker compose build web`      | `docker compose up -d --no-deps web`      |
| Hub, or the Caddyfile | `docker compose build hub edge` | `docker compose up -d --no-deps hub edge` |

Clearing both fields restores the full-stack deploy.

<Callout type="error" title="--no-deps is not optional">
  Without it, Compose starts what `web` declares in `depends_on` — `hub` — and recreates it, because
  its image tag moved with the commit. That is the exact restart this avoids. Never add
  `--remove-orphans` or `--force-recreate` either: both reach past the service you named.
</Callout>

The Caddyfile is baked into the `edge` image rather than bind-mounted, because
Coolify turns a file bind mount into one it manages itself — the container gets
the copy stored on the server, not the one in the repository. So a routing
change means rebuilding `edge`.

## The external database

This file ships no database service and no data volume. `DB_PROVIDER` has to
agree with `DATABASE_URL` — **`mysql`** for MariaDB or MySQL, `postgresql` for
Postgres — and it is used twice per app service: as a **build arg**, because
the Prisma Client is generated into the images, and as a **runtime env**,
because it selects which migration history `prisma migrate deploy` applies.
Changing it is a rebuild, not a restart.

<Callout type="warn">
  The URL is resolved inside the container, so it needs the database's **internal** hostname, which
  only resolves with [Connect to Predefined Network](#set-two-switches-before-the-first-deploy) on —
  a public one works until Coolify's firewall or a restart moves it. And the two migration histories
  do not convert into each other: pointing this stack at a database of the other kind starts an
  empty schema rather than migrating anything.
</Callout>

## Where the domains come from

Coolify generates each domain from the `SERVICE_URL_*` placeholder the service
declares, and the apps read the generic form of it:

| Variable                | Value                           | Read by                                          |
| ----------------------- | ------------------------------- | ------------------------------------------------ |
| `SERVICE_URL_EDGE_8080` | carries `:8080`                 | the proxy, for routing                           |
| `SERVICE_URL_EDGE`      | `https://agents.example.com`    | `MAGNEMITE_PUBLIC_URL` — every artifact URL      |
| `SERVICE_URL_WEB_3000`  | carries `:3000`                 | the proxy, for routing                           |
| `SERVICE_URL_WEB`       | `https://magnemite.example.com` | `MAGNEMITE_DASHBOARD_URL` — auth and alert links |

The declarations are written in **map** form (`SERVICE_URL_EDGE_8080:`, no
value). The list form means the same thing to Compose, but Coolify's compose
preview mis-converts it and the deploy fails with `non-string key in
services.edge.environment: 0`. Writing `${SERVICE_URL_EDGE_8080}` as the value
is also wrong — Compose interpolates a variable that does not exist yet and
blanks it out.

`SERVICE_PASSWORD_*` and `SERVICE_BASE64_*` have none of this problem —
generating a secret once has nothing to keep in sync.

Upgrading from the version that had no placeholders: keep the domain, drop the
`:8080` / `:3000` suffix from the Domains tab, and leave
`MAGNEMITE_PUBLIC_URL` set if you already have it. No box needs re-flashing — a
box only ever knows the URL.

## Why there is still a Caddy

Traefik routes; it does not serve files, and the `artifacts` volume belongs to
this stack. Without `edge`, every ~170 MB bundle would be read and pushed by
Node. It mounts the volume read-only, answers `/files/*` with native `Range`
behind a `forward_auth` call to the hub's `/internal/authz`, proxies
`/ws/device`, `/api/enroll`, `/api/logs/*` and `/healthz`, and 404s everything
else — which is what keeps `/internal/*` unreachable from outside.
