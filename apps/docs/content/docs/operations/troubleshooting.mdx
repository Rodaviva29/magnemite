## DNS on Android

<Callout type="warn" title="Symptom">
  The agent never connects, and its log repeats one line:

```
lookup magnemite.example.com: no such host
```

Meanwhile the box browses the web perfectly, and `ping` from `adb shell`
resolves the same name without trouble.

</Callout>

### Why it happens

The agent is built with `CGO_ENABLED=0` so it is one static binary that needs no
NDK to cross-compile and no shared libraries on the box. The cost is that Go
stops calling the system resolver and uses its own, written in Go — and that
resolver learns which nameservers to use by reading `/etc/resolv.conf`.

Android does not have that file. Bionic, Android's libc, asks the `netd` daemon
over a socket instead, and publishes the current servers as system properties:

```sh
adb shell getprop net.dns1
```

So everything on the box resolves names except a CGO-free Go program, which
finds no config, has no servers to ask, and fails every lookup.

### The fix

It lives in `agent/internal/netfix`. At startup the agent checks for
`/etc/resolv.conf`; if the file is missing it installs a `net.Resolver` whose
dialer walks this list, rotating to the next entry whenever a server refuses a
connection — common on a LAN where the router's resolver black-holes.

| Order | Nameserver              | Where it comes from                  |
| ----- | ----------------------- | ------------------------------------ |
| 1-4   | `net.dns1` … `net.dns4` | `getprop`, i.e. what `netd` is using |
| 5     | `1.1.1.1`               | Fallback                             |
| 6     | `8.8.8.8`               | Fallback                             |

<Callout type="info" title="Consequences worth knowing">
  On a box whose DNS is genuinely broken, set `serverUrl` to a bare IP and skip
  resolution entirely.

And if you ever rebuild the agent with CGO enabled, this code becomes dead
weight — but so does the single-binary cross-compile.

</Callout>

## What version is actually running

The **Status** page carries the version of every piece.

| Card        | Reports                                                          |
| ----------- | ---------------------------------------------------------------- |
| Dashboard   | Its own `web=` version, Next.js and Node                         |
| Hub         | Its own `hub=` version, Node, and the `agent=` it is handing out |
| Database    | The Postgres server version and the Prisma client's              |
| Public edge | Whatever answers on the boxes' URL, from its `Server` header     |
| Rotom       | The scanner versions across the fleet, counted                   |

> Each number comes from the matching line of the repo's `VERSION` file.

## Reading what the box actually printed

The **⋯** menu on a device page has **Logcat (.zip)** for a snapshot you can
keep and **Live logs** for logcat as it happens. What each contains, and what to look for, is in
[reading a box's logs](/docs/fleet/logs).

## An agent that will not update

The hub only sends `agent_update` to a box whose reported version differs from
its target, that is not mid-job, and whose ABI it has a build for. Check
the **Status** page for the target version and `AGENT_AUTO_UPDATE`, the
device page for the version that box reports, and the box's own log for
`self-update:` lines. 

Check the full flow in [updating the agent](/docs/fleet/agent#the-agent-updates-itself).

## Small `/data`

Boxes need roughly **450 MB** free: a 172 MB bundle unpacks to ~250 MB and both
sit on disk at once. The agent refuses to start an install below that rather
than filling the partition. Devices table shows free space per device and warns under 500 MB, when things are already tight.

## Egress

A full rollout to 200 boxes is ~35 GB off your server. **Settings → Tuning → Max concurrent jobs** paces it

<Callout type="error" title="Check your traffic allowance">
  If your ISP or cloud provider has a cap, check it before you start a rollout.
</Callout>

## A box enrolled but never appears online?
I know the feeling, such a headache. Check the following:

| Check                  | How                                                                                    |
| ---------------------- | -------------------------------------------------------------------------------------- |
| Right URL?             | `serverUrl` must be the **hub** domain (`MAGNEMITE_PUBLIC_URL`), not the dashboard's.  |
| Right port on Coolify? | The edge domain's port in the Domains tab must be `8090`, or the proxy misses Caddy.   |
| Approved?              | With auto-approve off, a box sits as _pending approval_ and receives nothing.          |
| Token still valid?     | A revoked enrollment token blocks _new_ enrollments; a revoked device is disconnected. |
| DNS?                   | See [DNS on Android](/docs/operations/troubleshooting#dns-on-android) above.           |

## Downloads 401 at the edge

`/files/*` is gated by `forward_auth` against the hub's `/internal/authz`. A 401
means the device token the box presented is not one the hub recognises, most
often a box restored from a backup image whose device row was deleted. Delete
its `config.json` device token and let it enroll again.
